# Conversation: Mural integration status

Updated 16 September 2026. This document describes the code implemented in Kakehashi and the checks actually performed. **It is not a claim of complete live runtime parity with Mural.** The source inventory is [mural-feature-inventory.md](./mural-feature-inventory.md).

## Access and setup

The **Japanese conversation** entry on Home opens the standalone Conversation screen (`/conversation`) and is reserved for the authenticated WaniKani account named `Portego`. The Home widget defaults immediately below **Extra Study**, including a one-time insertion into existing saved Home layouts. Portego can move, remove and re-add it through Home customization. Both the widget and its customization option are hidden for other accounts, and the route also checks access before mounting. The entry reuses the animated Conversation orb without starting an audio session; its animation pauses when Home is unfocused or the app is in the background and honors Reduce Motion. This screen has its own **Talk / Themes / Words** bottom navigation and a **Home** control that ends/saves the current session and returns to the Home screen. It sits outside Kakehashi's global tabs; existing saved tab orders are migrated to remove the old Conversation tab. Archive files and API credentials are scoped to the WaniKani account ID. This is a private client feature gate; there is no new server-funded OpenAI endpoint.

1. Use a Kakehashi native build containing WebRTC, call-audio routing, file picking and sharing dependencies. Production iOS **1.5.0 (build 83)** was confirmed to include these modules and accepts the subsequent 1.5.0 UI updates over OTA. A JavaScript-only update or Expo Go cannot add missing native modules to older binaries; attempting voice without them explains that a new build is needed.
2. For local development, install the repository dependencies, update iOS pods when needed, and use the existing `npm run ios` or `npm run android` build flow. Preserve the checked-in native projects and their existing custom integrations; a clean native regeneration is not required for this feature.
3. Sign in to Kakehashi as Portego and choose **Japanese conversation** on Home. Select a translation/explanation language (English by default), and accept the OpenAI processing disclosure. Practice is always Japanese. The updated disclosure includes relevant WaniKani learning information; prior consent must be renewed before model requests resume.
4. In Conversation settings, enter a personal OpenAI project API key with access to the configured models. The implementation uses `gpt-live-1` through `/v1/live/sessions` and `gpt-5.6-luna` through `/v1/responses`. Availability and account access must be confirmed with the actual project; this feature does not silently substitute a different model or fake a conversation.
5. Allow microphone permission when starting voice. Type instead can start a written conversation without opening the microphone. Usage is billed to the user's OpenAI project; the local duration limit is not an account billing cap.

Native keys use Expo SecureStore and are excluded from archives. The web implementation keeps the key only in memory for the current visit. No provider key is embedded in the application, stored in the learning JSON, or added to repository configuration.

## Kakehashi learning integration

GPT-5.6 Luna now has four read-only tools, used in typed conversation, written help and GPT-Live client delegation. They use the existing signed-in WaniKani token locally. The token is sent only to WaniKani; OpenAI receives normalized learning results. The separate OpenAI project key remains necessary to run the tutor.

| Tool | Information available |
| --- | --- |
| Learning profile | WaniKani level, vacation state, started kanji/vocabulary counts, lessons and review summary |
| Study items | Studied, currently due or weak kanji/vocabulary, with readings, meanings and available progress; up to 30 items |
| Subject search | Japanese characters, readings or English meanings; exact Japanese slug search or a bounded selection of up to five levels |
| Subject details | Meanings, readings, example sentences, assignment/SRS status and review accuracy for up to 20 subjects |

Each new voice or written conversation now attempts to load the learner's WaniKani level and up to eight actual studied vocabulary items before the first tutor request. This uses the same authenticated adapter, with one eight-second deadline for the whole load; a failure permits ordinary Japanese practice and explicitly tells the model what was unavailable. Continuing a written conversation in voice reuses its context. The Talk screen shows loading, loaded, partial or unavailable state, and its WaniKani row opens the actual words, readings and meanings provided. No level or vocabulary is fabricated. The model is asked to use one to three of these words naturally while following the chosen topic; the UI reports context loaded, not proof that the model used every word.

Previously, learning reads depended entirely on Luna deciding to call a tool, and the screen did not display their results. The tools remain available for relevant follow-up questions, such as due or difficult items. Live voice delegates those requests to Luna. These are actual function calls through `/v1/responses`, with complete stateless tool-result/reasoning continuation. The loop has a 45-second deadline, at most eight calls across four rounds, and reports combined token/search usage. Study queries return explicit coverage when results are sampled; weak means less than 85% review accuracy, not a diagnosis of speaking weakness.

The local adapter fixes the API origin, endpoints and GET method, validates parameters, verifies token ownership against `/user`, and cancels on account changes. Pagination cannot change the origin or filters. It shares Kakehashi's WaniKani rate limiter and request deadlines. Error bodies, keys, headers, account identifiers and raw API responses are excluded from model results. API behavior follows the [official WaniKani API documentation](https://docs.api.wanikani.com/20170710/).

This integration reads WaniKani learning context. It does not submit reviews or write conversation outcomes into WaniKani, JPDB or Bunpro. Conversation evidence and history remain in the feature's account-scoped archive. WaniKani progress does not award conversational recall or change the speaking challenge directly.

## Voice selection and previews

Open **Conversation settings → Japanese voice** to choose any of the 22 GPT-Live voices. Marin remains the default. The choice is saved per account, included in backups, and captured when connecting; a change during a conversation applies to the next voice session. Practice instructions continue to request Japanese with the chosen voice.

Voice previews are bundled audio assets. Tapping Preview uses only the local Expo audio player: it does not read the OpenAI key, open a connection, request AI consent, record a microphone or bill the user, including the first play. The previous generate-on-first-play path and its account cache have been removed. Failed generation previously left no cached sample and caused the next attempt to retry a billed connection; its generic connection error did not establish that the key lacked permissions.

Reference recordings come from OpenAI's public Live/Realtime announcements and speech documentation, with exact source URLs, extraction or header-repair details, and file checksums in `src/features/conversation/assets/voice-previews/provenance.json`. Twenty recordings are in English; Bossa and Tempo are in Brazilian Portuguese. Some originate from earlier speech models, rather than the current Live model. The picker states these limits explicitly, and practice remains Japanese. Changing voices still applies to the next practice connection. Browsers load the included static media from the app origin; native updates install every recording before activation for offline playback.

Closing the sheet, leaving the screen, backgrounding, changing accounts or starting practice stops playback and invalidates pending audio setup. Preview is disabled during a practice session. A bounded playback-start timeout reports local playback failure without suggesting key or model-access changes.

## Keyboard handling

Conversation pages and the shared sheet host use keyboard-aware scrolling. All nine input sites register the focused field and scroll it into the visible area as focus, keyboard height or multiline content changes. iOS uses interactive drag dismissal and native keyboard insets; Android uses resized windows and drag dismissal. Taps on controls stay responsive with the keyboard open. Changing internal pages, switching nested sheets and closing modals dismiss the keyboard. Multiline fields have bounded heights and can scroll internally, so long text does not cover the whole screen. The existing single native modal host remains in place.

## App appearance

Conversation follows Kakehashi's saved Light, Dark, Midnight, Sepia or System mode, without a separate appearance setting. Its canvas, cards, topic tiles, text, errors, controls, search fields, sheets, voice picker and tab colors use the shared app palette. The animated orb on both Home and Talk derives its gradient, highlights, satellites, shadow and listening rings from the same primary, secondary and accent colors. Motion and audio responsiveness are unchanged.

The shared native theme provider now owns iOS appearance across all routes. The duplicate Home and Bunpro tab overrides were removed so leaving a tab no longer clears an explicit app appearance. Liquid Glass remains the native iOS material. iOS keyboard appearance and input cursor colors follow the active palette; changing appearance does not dismiss a draft, replace the sheet presenter or remount the conversation controller.

## Native Conversation tabs

Talk, Themes and Words are now child routes of `/conversation`, using the same Expo Router native tab navigator and compatibility check as Home. iOS 26 supplies the real Liquid Glass tab bar. Other supported platforms retain standard tab navigation, matching Home's fallback. This uses native modules already present in the 1.5.0 iOS build and is OTA-compatible.

One account-scoped conversation controller lives above all three routes. Changing tabs preserves the active call, transcript, selected theme and learning context. Leaving Conversation, backgrounding or signing out still stops and saves the session. Each page retains its Home exit; it waits for session cleanup before returning to the Home screen. There is no second global tab bar inside Conversation. Native screen safe areas reserve the real tab bar height, keeping the WaniKani row and other controls above it without a hard-coded tab height.

## Language and rendering substitutions

These are explicit implementation choices, not claims that the original platform rendering or dictionaries were copied exactly.

- **React Native UI:** Screens, sheets, themes and word rows are React Native and follow Kakehashi's app palette. Local static Nunito 400/600/700/800 faces supply rounded typography in place of Apple's rounded system font; explicit face selection fixes the source variable font's thin native default. Ionicons replace SF Symbols. The feature keeps its own Talk/Themes/Words navigation inside the Kakehashi destination.
- **Orb rendering:** The orb retains a twelve-point quadratic outline, slow deformation/drift, colored highlights, satellites, floor shadow, listening rings and microphone/output-driven scaling. Reanimated runs the shape/motion on the UI thread and React Native SVG blends radial color layers. This replaces SwiftUI `MeshGradient`; the color field is not a pixel-identical mesh simulation. Motion pauses when inactive and honors Reduce Motion.
- **Platform surfaces:** Native React Native/Expo surfaces replace SwiftUI/Compose-specific materials and sheets. Layout adapts to width/font scale; exact Liquid Glass material and platform font metrics are not reproduced.
- **Mandarin readings:** `pinyin-pro` with `@pinyin-pro/data/modern` replaces Apple's system lexical readings and Mural Android's bundled python-pinyin dictionaries. It runs offline, preserves original transcript text and renders readings separately. Dictionary disambiguation can differ from the native originals; it is a reading aid, not pronunciation scoring.
- **Word boundaries:** `Intl.Segmenter` is preferred where available. Offline Mandarin segmentation and TinySegmenter for Japanese cover native engines lacking it. Punctuation, whitespace, emoji and mixed scripts remain in the selectable original text. Japanese fallback boundaries are statistical approximations, not a morphological dictionary analysis.
- **Japanese practice:** Japanese (`ja`, `ja-JP`) is the only practice language in Kakehashi, with a six-stage policy and culturally adapted scenarios. Mural's original eight language modules remain only for archive compatibility; loading or importing old preferences cannot reactivate another practice language. Non-Japanese history is preserved in backups and is not automatically assessed. All 12 original meaning-language choices remain, with English as the default. Japanese records cannot be imported into an older Mural build that has no Japanese module.
- **Language identification:** React Native has no common equivalent of Apple's NaturalLanguage recognizer. A structured helper request supplies a conservative language/confidence check. This adds request latency/cost and is not the original fully local classifier. Target-language instructions remain in force when that check is unavailable.
- **Local ownership:** Existing Kakehashi authentication replaces Mural's app onboarding/account identity. Learning remains on this device, separately per WaniKani account, rather than syncing through a new Kakehashi service.

## Deliberately excluded service infrastructure

Mural's hosted account provisioning, guest minutes, subscriptions/top-ups, payment recovery, Apple/Google account deletion and service-admin tooling were not copied. Its README describes hosted free conversations/minute purchases as inactive; this integration uses the personal BYOK model inside Kakehashi.

The additional Android assistant-report submission workflow and report backend are also not implemented. There is no configured Mural report/account service in Kakehashi. This omission is separate from the conversational learning features.

The feature credits Mural in settings. Full notices are readable offline through Conversation settings → Open-source licenses. Copies are retained under `licenses/`; dependency attribution, including the upstream/metadata license discrepancy for the Mandarin data package, is recorded in `THIRD_PARTY_NOTICES.md`.

## Remaining live acceptance checks

These features are implemented but must be exercised with a real supported OpenAI project key and appropriate devices before calling runtime parity complete:

1. Successful live startup on both platforms, audible speaker output, target-language speech, live user/assistant captions, correct metering and permission denial/retry.
2. Full-duplex interruptions, microphone mute/unmute, Bluetooth/headset changes, phone/audio-focus interruption, backgrounding/tab changes and restoration of the rest of Kakehashi's audio behavior.
3. Live meanings, lookup, language drift, typed/voice continuity, delegated help, Luna's WaniKani tool selection/results and current web-topic discussion against real provider responses.
4. Real post-conversation assessments and delayed/failing provider responses; account changes and app termination during saving.
5. Visual comparison on physical devices and accessibility checks at large text sizes, VoiceOver/TalkBack and Reduce Motion. The source-inspired layout is implemented; pixel-identical rendering is not asserted.
6. Native share/document picker flows and importing an actual exported file on both platforms, in addition to the codec/storage tests.
7. Confirm the selected voice in a subsequent credentialed Japanese conversation. The bundled preview recordings require no credentials or provider session; they demonstrate voice identity in their recorded language rather than proving Japanese output from a live connection.

No live provider credential was supplied for these checks. There are no canned tutor replies or fabricated learning records standing in for successful requests.
