# Kakehashi ASO copy and review-prompt audit

Prepared 16 September 2026. Primary market: United States. Secondary market: Spain. These are proposed changes for review, not published metadata or promises of a particular ranking.

## The change to test first

Use **Kakehashi for WaniKani** as the Google Play title. The currently verified title is just **Kakehashi** and its short description is **Wanikani Companion App**. Adding the service name to the title makes the relationship immediately visible to someone searching for it. The discoverability effect is a hypothesis to measure, not a known ranking increment.

The [US iOS listing](https://apps.apple.com/us/app/kakehashi-for-wanikani/id6757765444) already has **Kakehashi - For WaniKani** in the name and **Learn Japanese Kanji & Vocab** as the subtitle. **Keep the current iOS names initially:** **Kakehashi - For WaniKani** in English and **Kakehashi - Para WaniKani** in Spanish. They already contain the target service name. After establishing the baseline, test the task-focused subtitle below as a separate iOS change. Do not present punctuation or putting a keyword first as a proven ranking technique.

Apple identifies name, subtitle and keywords among searchable metadata. Its guidance encourages distinctive names and specific keywords, and discourages duplicate words and competing app names. Google requires descriptive, relevant metadata and rejects repetitive keywords and deceptive claims. ([Apple searchable information](https://developer.apple.com/help/app-store-connect/create-an-app-record/view-and-edit-app-information), [Apple product-page guidance](https://developer.apple.com/app-store/product-page/), [Google metadata policy](https://support.google.com/googleplay/android-developer/answer/9898842?hl=en))

This version deliberately prioritizes the task behind a WaniKani search and four benefits already described on the public listing: reviews/lessons, anime listening, NHK reading and progress statistics. It avoids promising that local working-tree additions have shipped.

Kakehashi is an unofficial WaniKani companion for kanji reviews and lessons. Keep up with your study routine, then practice what you know with anime dialogue and NHK news.

REVIEWS AND LESSONS
Complete your WaniKani reviews and lessons in one app. Adjust batch sizes and question order to fit your study routine, then check your session statistics.

JAPANESE IN CONTEXT
Practice listening with short anime dialogue clips. Read NHK articles with kanji readiness indicators to see how the text matches your knowledge.

PROGRESS YOU CAN FOLLOW
Explore your kanji and vocabulary statistics, review activity, and progress across JLPT and Joyo levels. See what you have learned and where to focus next.

The description can support a clearer download decision. On iOS, do not sell rewriting it as a substitute for name, subtitle and keyword work: Apple's documented searchable fields are listed above, and Apple specifically says promotional text does not affect search ranking. The draft does not aim for an invented keyword-density percentage. ([Apple product-page guidance](https://developer.apple.com/app-store/product-page/))

## Review-prompt audit: local code, release status unverified

This is a static inspection of the current working tree, not a runtime audit or verification of a released build. The dashboard file has uncommitted modifications. No code was changed during this audit.

| Observed behavior | Practical implication |
|---|---|
| The dashboard checks `currentStreak >= 5`, then a persisted key named `rate_app_streak_prompted_<userId>`. | Only users reaching this consecutive-use milestone qualify; frequent users who miss days may never qualify. This is an eligibility choice, not evidence of a defect. |
| It writes that key before requesting the native review flow, and removes it only if the request throws. | A successful API call that displays no dialog can spend the user's only persisted opportunity on that device. The marker is effectively permanent until local storage is cleared. |
| The call sits in a dashboard effect; it is not tied specifically to completing a study session. | It may run when entering the dashboard after streak data loads, rather than during a deliberate pause after completing study. |
| It logs the automatic request as source `Streak` through `logRateAppClick`. | This record is a request attempt, not a click, confirmed dialog impression or submitted review. |
| The settings and tip-page buttons open the store URL first, then fall back to the native request API. | The direct-store path fits an explicit “Rate App” action. The native fallback can still silently show nothing; returning `true` from the helper does not prove that a review UI appeared. |

Local evidence: [streak threshold and cache key](/Users/pedroortego/Code/Kakehashi/app/(app)/(tabs)/index.tsx:82), [eligibility and request flow](/Users/pedroortego/Code/Kakehashi/app/(app)/(tabs)/index.tsx:523), [store URL and fallback service](/Users/pedroortego/Code/Kakehashi/src/services/rateAppService.ts:15), [event payload](/Users/pedroortego/Code/Kakehashi/src/services/rateAppService.ts:66), [settings action](/Users/pedroortego/Code/Kakehashi/src/features/settings/useSettingsController.ts:1306), [tip-page action](/Users/pedroortego/Code/Kakehashi/app/(app)/tip-developer.tsx:256).

Apple recommends requesting after successful completion of an activity, without interrupting the user, and avoiding app-launch timing. Apple controls whether a request is displayed and limits display frequency. Google also applies a quota; its API does not indicate whether the dialog appeared or whether the user reviewed. Therefore an API completion cannot serve as a review-conversion event. ([Apple request guidance](https://developer.apple.com/documentation/storekit/requesting-app-store-reviews), [Google quotas and timing](https://developer.android.com/guide/playcore/in-app-review), [Google API completion semantics](https://developer.android.com/guide/playcore/in-app-review/kotlin-java))

Recommended bounded improvement, if this matches the shipping code:

1. Preserve the native automatic prompt, but consider eligibility based on meaningful use over several days plus completed study sessions. Ask after a completed session when the user pauses, rather than solely from dashboard entry. Do not condition access on an expressed positive opinion or an intended star score.
2. Replace the permanent boolean with the last request date and app version. Choose a conservative retry policy, such as at most one attempt per 120 days with meaningful continued use, and treat that interval as a product choice, not an Apple or Google guarantee. A new version alone should not reset the interval.
3. Separate `review_prompt_requested` from `review_store_link_opened`. Measure those events by platform and app version alongside store-reported ratings over time; do not call them reviews submitted or dialog views.
4. Keep explicit settings/tip actions linked to the store listing. Google specifically recommends redirecting to Google Play for a button because the native flow may be suppressed. Do not show a custom “Do you like the app?” prescreen, reward reviews, or ask only for positive ratings. ([Google in-app review guidance](https://developer.android.com/guide/playcore/in-app-review))

These changes could recover missed opportunities for authentic feedback. They do not establish that review volume caused the current search rank, and they cannot guarantee first position. Verify release parity before implementation; no broader redesign is needed for this experiment.
