# iOS recognition of short Japanese review answers

Investigated 2026-09-18 against Apple's documentation and the installed `expo-speech-recognition@2.1.5` source. These findings identify configuration and lifecycle improvements; they do not establish recognition accuracy on a physical iPhone.

## Findings

1. **The missing first syllable is a documented recognizer limitation.** The library specifically describes short syllables, letters, and numbers producing no result until more speech arrives. It recommends `iosTaskHint: 'confirmation'`, which this app already uses. Apple describes confirmation as short commands such as yes/no; there is no documented Japanese-specific task hint or phonetic-output option. Keep confirmation initially rather than assuming dictation/search is better. [Library short-prompt guidance](https://github.com/jamsch/expo-speech-recognition/blob/v2.1.5/README.md#improving-accuracy-of-single-word-prompts), [Apple confirmation hint](https://developer.apple.com/documentation/speech/sfspeechrecognitiontaskhint/confirmation)

2. **End an utterance without ending hands-free mode.** Apple's `endAudio()` declares that input is complete; `finish()` processes audio already accepted. Installed v2.1.5 `stop()` reaches both operations, while `abort()` cancels without a final result. Calling `stop()` after detected speech followed by silence gives the recognizer an explicit endpoint, including when no partial transcription arrived. Restart after its `end` event if the answer is still pending and hands-free mode remains enabled. This is a supported mechanism, but improved results for `つ`/`よ` are a hypothesis requiring device testing. [Apple endAudio](https://developer.apple.com/documentation/speech/sfspeechaudiobufferrecognitionrequest/endaudio()), [Apple finish](https://developer.apple.com/documentation/speech/sfspeechrecognitiontask/finish()), [v2.1.5 implementation](https://github.com/jamsch/expo-speech-recognition/blob/v2.1.5/ios/ExpoSpeechRecognizer.swift)

3. **Do not wait for iOS `speechstart`/`speechend` to implement that endpoint.** The library documents `speechstart` as occurring only after a recognition result, and `speechend` as unsupported on iOS. `volumechange` works independently of text and is opt-in. It reports approximately -2 to 10, with values below zero described as inaudible. The native implementation measures audio power, not voice identity: background noise can trigger it. Use a sustained activity threshold and a quiet interval, never a timeout measured from microphone activation. The exact activity/silence durations and thresholds are application heuristics. [v2.1.5 event documentation](https://github.com/jamsch/expo-speech-recognition/blob/v2.1.5/README.md#speech-recognition-events)

4. **Forcing on-device recognition is not an accuracy guarantee.** Apple explicitly cautions that on-device requests are less accurate. Allowing Apple's default server-capable behavior for Japanese is a defensible experiment; it may introduce connectivity dependence and sends audio to Apple when the system chooses server recognition. `requiresOnDeviceRecognition: false` permits server use; it does not force it. Keep the privacy/connectivity consequence explicit. [Apple requiresOnDeviceRecognition](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition)

5. **The library's public on-device support check is not locale-specific.** In v2.1.5, `supportsOnDeviceRecognition()` constructs `SFSpeechRecognizer()` without a locale. During `start`, however, native `prepareRequest` checks the actual recognizer before applying `requiresOnDeviceRecognition`. A support result for the device's default locale should therefore not be interpreted as a Japanese capability test. Apple also states that a supported locale does not guarantee current recognition availability. [v2.1.5 module source](https://github.com/jamsch/expo-speech-recognition/blob/v2.1.5/ios/ExpoSpeechRecognitionModule.swift), [Apple supportedLocales](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportedlocales())

6. **Use focused vocabulary hints, without treating them as an answer restriction.** Apple recommends brief phrases and at most 100 contextual strings; hints increase recognition likelihood rather than constrain the output vocabulary. Supplying the current valid readings in both hiragana and katakana is a reasonable experiment, but no primary source found establishes that katakana fixes isolated kana. Avoid blanket `4 → しき` replacement: the transcript contains no evidence of the missing `き`. Inspect alternatives and prefer complete exact reading matches before accepting a numeric/short partial result. [Apple contextualStrings](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/contextualstrings)

7. **Repetitions need utterance boundaries, not unconditional text deduplication.** Apple segments include text, start time, duration, confidence, and alternative interpretations. The library exposes segment text/timing/confidence and whole-transcript alternatives, but not `alternativeSubstrings`; partial confidence may be zero. A visible pause between independently recognized repeated segments can support treating the latest one as a retry. A single `つつ` segment cannot reliably prove two attempts, and deduplicating arbitrary Japanese text can turn an incorrect answer into a correct one. Prefer fresh recognition requests after endpoints and conservative fallback handling. v2.1.5 also marks some iOS 18 results final using speech metadata rather than Apple's actual `isFinal`, so wait for the library's `end` event before starting a replacement request. [Apple SFTranscriptionSegment](https://developer.apple.com/documentation/speech/sftranscriptionsegment), [v2.1.5 result mapping](https://github.com/jamsch/expo-speech-recognition/blob/v2.1.5/ios/ExpoSpeechRecognitionModule.swift), [v2.1.5 result types](https://github.com/jamsch/expo-speech-recognition/blob/v2.1.5/src/ExpoSpeechRecognitionModule.types.ts)

## Bounded implementation direction

- Preserve continuous hands-free mode at the application level, but finalize individual Japanese attempts with `stop()` after audible input followed by a quiet interval. Keep waiting indefinitely before the user speaks.
- Show incoming text immediately. Do not submit a short partial hypothesis while the user is still speaking or while finalization is pending; a partial `4` must have a chance to become a longer reading.
- Keep `confirmation`, punctuation disabled, and multiple alternatives. Deduplicate and cap short contextual hints; test hiragana/katakana variants as an explicitly unproven improvement.
- Do not infer arbitrary expected answers from digits or merged repetitions. Apply exact matching to recognition alternatives and supported reading conversions.
- Compare local-only versus server-permitted recognition on a device before promising an accuracy improvement. Ensure permissions, offline errors, cancellation, and automatic restart remain correct if the policy changes.

## Larger follow-up if short readings remain unreliable

Apple introduced custom on-device language models in iOS 17, with weighted phrase training and explicit pronunciations. Customization is locale-specific, requires on-device requests, and model preparation can be expensive. The installed Expo bridge does not expose this configuration, so it requires native work and an evaluation dataset rather than a JavaScript option. This is a stronger vocabulary-control mechanism worth evaluating later; it is not evidence that isolated Japanese kana will automatically become reliable. [Apple WWDC23: Customize on-device speech recognition](https://developer.apple.com/videos/play/wwdc2023/10101/)

## Physical-device checks

Test `しき`, `つ`, and `よ` once each after 5–10 seconds of silent thinking; then retries separated by a pause. Include longer readings, actual repeated-kana words, incorrect readings, quiet speech, background noise, pronunciation playback, and switching between Japanese and English. Record raw alternatives and segment timing while testing, and compare iOS versions and recognition policies. Unit tests can validate lifecycle and matching rules, but cannot establish acoustic accuracy.

## Applied in this follow-up

Kept the confirmation hint; added kana/katakana/written-form hints and volume-based utterance finalization; permitted the normal iOS recognition service rather than forcing local-only decoding. Japanese grading waits for finalized text, correct candidates use a shorter quiet window, and timestamped retries can be separated without deduplicating actual words. A final numeral without a matching reading remains a retry, never a substitution such as `4 → しき`. See [validation notes](../docs/review-input-validation.md#short-japanese-utterances-and-listening-feedback-2026-09-18) for timings, regression coverage, and remaining device checks.
