# Duolingo Japanese recognition and iOS processing diagnostics

Investigated 2026-09-18 using Duolingo's public material, Apple's API documentation, and the installed `expo-speech-recognition@2.1.5` source. This supplements [the short-Japanese-utterance investigation](./ios-japanese-short-speech-recognition.md).

## What Duolingo publicly establishes

- **Phonetic grading can improve perceived recognition without changing the recognizer.** Duolingo describes changing Chinese speaking-exercise grading so that recognizer output with an equivalent pronunciation can pass despite different written characters. It reports a similar approach for Korean. This is directly relevant to kanji homophones, but the article does **not** establish that Japanese lessons use the same algorithm. [Duolingo: improving Chinese and other languages](https://blog.duolingo.com/improving-how-duolingo-teaches-chinese-and-other-languages/)
- **Its speaking interfaces include transcription.** Duolingo says that dictated answers appear as text and can be edited before submission. That distinguishes recognizing speech from deciding whether the recognized answer should pass. The article does not disclose the Japanese recognizer, thresholds, language model, or kana-specific processing. [Duolingo: extra pronunciation practice](https://blog.duolingo.com/sneaky-pronunciation-practice/)
- **Duolingo has in-house speech and pronunciation models, but the documented use here is animation.** It analyzes generated character audio to obtain word/phoneme timings for lip synchronization. This is not evidence that those models recognize Japanese learner answers. [Duolingo: character visemes](https://blog.duolingo.com/world-character-visemes/)
- **Other Duolingo speech products do not answer this question.** Its pronunciation-scoring research explicitly concerns spoken English in the Duolingo English Test. Neither that model nor Video Call technology should be attributed to Japanese kana lessons without a separate disclosure. [Duolingo English Test: pronunciation-scoring research](https://blog.englishtest.duolingo.com/new-research-in-language-learning-a-pronunciation-scoring-model-built-around-intelligibility-not-imitation/)

No Japanese/kana-specific engine, constrained decoder, phoneme scorer, or recognition configuration was identified in the first-party sources reviewed. The historic microphone-help URL now redirects to the generic help page; third-party quotations of the old Apple/Google engine guidance were not used as evidence of current Japanese behavior. [Former microphone article](https://support.duolingo.com/hc/en-us/articles/204642264-My-microphone-is-not-working-How-can-I-fix-it-)

## Implication for Kakehashi

The transferable, documented principle is to grade a supported pronunciation rather than require one particular written transcription. For example, a different kanji word with the same reading can be valid evidence; the digit `4` alone cannot establish that the speaker completed `しき`. This is an application-design inference from the phonetic-grading approach, not a claim about Duolingo's Japanese implementation. Expected-answer hints and reading conversion do not repair audio the recognizer never decoded.

The library documents absent results for short syllables, letters, and numbers and recommends the confirmation task hint. Apple also offers locale-specific custom language models, including phrase weighting and pronunciations, through native APIs. That is a future experiment requiring device evaluation, not an exposed Expo configuration switch or a proven isolated-kana fix. [Library short-prompt guidance](https://github.com/jamsch/expo-speech-recognition/blob/v2.1.5/README.md#improving-accuracy-of-single-word-prompts), [Apple: custom on-device models](https://developer.apple.com/videos/play/wwdc2023/10101/)

## What the debug tool can truthfully show

Apple's `requiresOnDeviceRecognition` is a **request policy**, not execution telemetry. Setting it to `true` prevents network transmission only when the recognizer supports on-device recognition; `false` removes that requirement and must not be labeled proof of cloud execution. `supportsOnDeviceRecognition` describes capability, not which path a particular utterance used. [Apple: request policy](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition), [Apple: local capability](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition)

The documented task, result, and metadata interfaces expose progress, errors, transcriptions, timing, and voice analytics; none provides a field reporting actual cloud/local execution. The installed Expo bridge likewise emits only finality and transcription data for results. Therefore automatic-mode diagnostics must report the actual execution location as **unavailable**, even when cloud processing is allowed. [Apple: recognition task](https://developer.apple.com/documentation/speech/sfspeechrecognitiontask), [Apple: result](https://developer.apple.com/documentation/speech/sfspeechrecognitionresult), [Apple: metadata](https://developer.apple.com/documentation/speech/sfspeechrecognitionmetadata), [Expo result mapping](https://github.com/jamsch/expo-speech-recognition/blob/v2.1.5/ios/ExpoSpeechRecognitionModule.swift)

Two bridge details affect any local-only experiment:

1. `supportsOnDeviceRecognition()` constructs `SFSpeechRecognizer()` without a locale. Its answer applies to the default recognizer and must not be presented as a verified `ja-JP` capability. [Expo support check](https://github.com/jamsch/expo-speech-recognition/blob/v2.1.5/ios/ExpoSpeechRecognitionModule.swift#L346-L349)
2. `prepareRequest` assigns `requiresOnDeviceRecognition` only when the actual locale recognizer supports local recognition. Otherwise it leaves Apple's default request policy. A genuinely local-only diagnostic mode needs a locale-specific capability check and must fail closed when that check is false or unavailable; displaying the requested JavaScript option alone cannot prove local processing. [Expo request preparation](https://github.com/jamsch/expo-speech-recognition/blob/v2.1.5/ios/ExpoSpeechRecognizer.swift#L511-L524)

Recommended compact fields: recognition provider, locale, requested processing policy, actual route availability, raw latest alternatives, partial/final status, and most recent error. A cloud/local badge inferred from network connectivity, confidence, response speed, or transcription content would be misleading. Manual offline success can demonstrate an offline trial, but cannot retrospectively identify the execution location of online trials.
