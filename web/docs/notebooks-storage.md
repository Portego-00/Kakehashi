# Notebook storage and deployment

Notebooks use the free BlockNote core editor on the web and in the mobile app's bundled Expo DOM editor, with a versioned, text-only JSON document in Supabase. The data model does not depend on React, DOM nodes, HTML, or BlockNote's runtime. Both clients read and write the same account's pages and references. See [Mobile notebooks](notebooks-mobile.md) for the Portego-only native integration.

## Deploy

1. Apply `supabase/migrations/20260907000000_notebooks.sql` through the project's normal reviewed Supabase migration workflow. Then apply `supabase/migrations/20260907010000_notebook_account_ids.sql` to support WaniKani’s opaque account IDs. These add only `public.notebook_states` and `public.compare_and_set_notebook_state`.
2. Configure `SUPABASE_URL` and **one server-only** `SUPABASE_SERVICE_ROLE_KEY` or `SUPABASE_SECRET_KEY` in the web deployment. Existing URL aliases `NEXT_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_URL` are supported. Do not expose the service credential through a `NEXT_PUBLIC_` variable. Public/anonymous credentials are deliberately insufficient.
3. Optionally set `NOTEBOOK_MAX_BYTES` to change the per-account compact UTF-8 JSON budget. The default is 1,048,576 bytes (1 MiB), clamped to 65,536–4,194,304 bytes. Page and sentence limits stay at 200 pages (including trash), 1,500 shared sentences, and 262,144 bytes per page.
4. Verify `GET /api/notebooks` authenticated as `Portego` returns `available: true`. Other accounts and demo sessions receive HTTP 403. A missing service credential returns `available: false`; a missing migration or failing database returns an error. A failed cloud write never reports a successful save.
5. Exercise two real accounts and confirm each sees only its own pages. Browser `anon` and `authenticated` database roles must be unable to select the table or execute its RPC.

The migration is additive. It does not copy, replace, or delete existing subject notes or custom context sentences. Applying it does not automatically migrate any local drafts; the client must explicitly submit notebook mutations.

## Privacy and write safety

The API derives ownership from the authenticated WaniKani session; callers never choose the storage owner. POST also requires an `X-Notebook-Account` header matching that verified identity, rejecting queued writes after an account switch. Verified WaniKani account IDs are opaque strings, including UUIDs; they are bounded to 128 URL-safe identifier characters. The browser endpoint rejects demo cookies and enforces same-origin POSTs. The [native endpoint](notebooks-native-api.md) verifies a bearer token and the Portego account gate instead of using browser sessions. Both use private/no-store responses, bound request bytes, and rate-limit reads and autosaves. Both legacy JWT service keys and current Supabase secret keys are supported.

The table has row-level security enabled and no grants for `public`, `anon`, or `authenticated`. The server service role may read it and execute the mutation function. The function has an empty search path and fully qualified table names. No direct browser access or public sharing is provided.

Each row has a revision. A conditional RPC writes only if that revision still matches. When another device changes a different item, the API rereads and reapplies the mutation, up to four attempts. Page and sentence revisions prevent stale edits to the same item from silently overwriting current content. Conflicts return HTTP 409 and must leave the client draft available for recovery. `append_blocks` applies to current contents and is idempotent by block ID. Identical page/sentence creation replays also succeed, supporting retries after an uncertain response.

## Portable format and APIs

The canonical definitions and pure validation/mutation logic are in `web/src/features/notebooks/model.ts`:

- `NotebookState`: `{ version: 1, pages, sentences }`.
- Optional `examples: { version: 1, status: "installed" | "removed" | "skipped", contentVersion?: number }` records the account's one-time onboarding choice and completed example-content update. Older documents without either optional field remain valid. Web and native clients use the shared `notebookExamplesNeedInitialization` helper to send a verified `initialize_examples` POST for missing examples or an installed tour with an older content version. Demo uses the same mutation in browser storage. `remove_examples` removes only the original sample pages, preserves personal descendants and reused/edited sentences, and keeps the marker so examples never return. Ordinary page deletion also preserves the marker.
- Pages include a stable ID, parent ID, title, icon, favorite, order, current block content, trash timestamp, timestamps, and revision.
- Sentences include one stable ID, Japanese, kana, English, associated subject IDs, timestamps, and revision.
- Standard blocks support headings, paragraphs, lists, checklists, toggles, quotes, dividers, code, and tables. Custom blocks support callouts, vocabulary, page links, and sentence references. Vocabulary can also be a `vocabularyMention` inline reference (its name differs from the block type because ProseMirror uses one node namespace). Formatting and links remain structured text.
- A sentence block contains only its sentence ID. Cards and pages resolve the same record. Editing that record updates every place that references it. Capturing an existing built-in example creates a private personal record; it never edits WaniKani's source text. Captures with equivalent Japanese and English deduplicate and combine subject associations.

`GET /api/notebooks` returns `{ available, state, revision, limits }`. POST accepts one of `create_page`, `update_page`, `append_blocks`, `trash_page`, `restore_page`, `delete_page`, `upsert_sentence`, `delete_sentence`, `initialize_examples`, or `remove_examples`. It returns the current state, account revision, limits, and `sentenceId` for sentence upserts (which may be an existing deduplicated ID). Creation uses caller-generated stable IDs; existing records require their expected item revision. Creating a sentence uses `expectedRevision: -1`.

The three-page example uses about 19 KB of compact text and the existing JSONB/CAS storage; no new database migration is required. It includes radical, kanji, and vocabulary references as blocks and inline mentions. Each account receives its own editable copy. Content version 2 adds the radical/kanji section to an existing context page only when none of that section's stable block IDs are present and its original introduction or following grammar heading still exists. Existing section blocks, including edits, reordered blocks and partial deletions, stay intact. Cleared or fully repurposed pages are left alone. Empty or legacy 📄 sample-page icons become 🧭, 🌱 and ✍️; other custom icons, titles, writing, sentences and personal pages stay unchanged. Deleted pages are never recreated, pages in Trash are not changed, and removed/skipped examples are never upgraded. A successful content-version marker makes subsequent loads a no-op; future template changes require an explicit versioned upgrade rather than silently replacing saved content.

Initialization respects quotas and never replaces personal content. Accounts without enough capacity for a new tour receive a skipped marker where it fits. An existing-tour upgrade that exceeds any page/account limit returns the original state without advancing its marker and can retry after space is freed. Failed optional writes leave existing notebooks readable. The account CAS retries concurrent initialization or upgrades against the latest document, preserving concurrent edits and respecting removal from another device. Changed pages increment their revisions so an already-open editor cannot overwrite the update with a stale draft. Document and marker-schema versions remain 1; clients loading the new optional content-version field need the updated validator, so an already-open older web bundle should be refreshed.

Moving pages cannot form a cycle. Trashing a parent trashes its active descendants. Restoring restores descendants from the same trash operation; restoring a child independently moves it to the root if its parent remains trashed. Permanently deleting a trashed page deletes its descendants and removes their page-link blocks. Shared sentences remain available to cards. Sentence deletion is refused while any page, including trash, references it.

The mobile app reuses this format and pure operations through a bundled BlockNote DOM editor. The browser endpoint continues to authenticate with the web's sealed session cookie and validate a web origin. The separate [native notebook API](notebooks-native-api.md) verifies the device's WaniKani bearer token and resolves the same opaque account ID. It does not trust a client-supplied owner ID or put the database service credential on the device. Deploy that route and configure `EXPO_PUBLIC_NOTEBOOKS_API_URL` to enable the [mobile integration](notebooks-mobile.md#configure-the-connection).

## Storage budget and operational tradeoffs

One account stores one current JSONB document, with no application revision history, duplicate sentence bodies, attachments, file uploads, images, audio, or video. Validation strips unsupported metadata, limits nesting and block counts, rejects media blocks and embedded data URLs, and allows only HTTP(S), mailto, and relative application links. JSON is serialized compactly and measured in UTF-8 bytes, so Japanese characters count correctly.

PostgreSQL can compress large JSONB values through TOAST. The application does not count compressed bytes: the predictable 1 MiB default is based on compact serialized text. The database has an 8 MiB defensive bound on PostgreSQL's expanded JSON text representation to cover its added whitespace and JSONB representation overhead while accommodating the server's 4 MiB absolute limit. Database indexes, row overhead, backups, and WAL are additional storage; this is not a promise of unlimited free hosting. At the default cap, 1,000 completely full accounts could hold roughly 1 GiB of uncompressed document payload before database overhead. Real usage may be much smaller, but operators should monitor Supabase's actual database capacity and egress.

Autosaves replace the current account document atomically. The client should debounce them and serialize its mutations. This keeps implementation and mobile sharing simple at the current bounded scale, but each update rewrites the row and returns its current state. Sustained heavy use increases write/egress costs even without application history. If account sizes or traffic grow, split pages and sentences into separate rows while preserving stable IDs and the API's item revision semantics.

Trashed pages still count toward storage until permanently deleted. Unreferenced sentences are deliberately retained because vocabulary cards may still use them; delete them through the explicit sentence operation when no longer wanted. Exports provide user-owned recovery without storing a second cloud copy.
